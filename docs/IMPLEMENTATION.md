# Как довести проект до рабочего процесса компании

Первая версия работает с файлами. Доступов к системам INTERTOP нет, конфигурация 1С, корпоративные шаблоны, роль пользователя и фактический процесс неизвестны. Указанные ниже интеграции — следующие этапы, а не заявленная функциональность текущего кода.

## Что нужно получить для следующего этапа

1. Одну обезличенную выгрузку поставки и пустой шаблон товарной карточки. Примеры должны сохранять структуру, типы столбцов, ведущие нули и варианты размеров/цветов.
2. Объяснение, что означает «ШНС заказа» в компании и какой идентификатор связывает поставку, заказ, товар и документы.
3. Название и версию конфигурации 1С, используемые формы импорта/экспорта, существующие обработки. Возможно, часть задачи уже решена встроенными средствами.
4. Перечень обязательных полей для сайта и для каждой товарной группы маркировки. Для размера/цвета нужны согласованные справочники и ключ идентичности товара.
5. Пример выгрузки полученных КМ без настоящих кодов, описание группировки по поставкам/GTIN и используемый формат сериализации.
6. Требования к фото: имена, папки, ракурсы, размеры, форматы, допустимость сжатия. Текущий модуль только копирует байты под новым именем.
7. Разрешённые способы установки и обработки локальных файлов на рабочем компьютере. Для прямой интеграции — тестовый контур и выданная ИТ-службой роль.

Для работы над структурой шаблонов доступы и пароли не нужны. Секреты не передаются в переписке и не хранятся в репозитории.

## Этапы

| Этап | Результат | Условие готовности |
| --- | --- | --- |
| 1. Проверка файлов | Текущая версия | Прогон демоданных и тестов |
| 2. Реальный шаблон | Чтение выгрузки и экспорт в согласованный шаблон | Обезличенный пример, правила обязательности, контроль итогов |
| 3. Пилот | Проверка на нескольких типичных поставках и исключениях | Сравнение с результатом опытного сотрудника; замер времени |
| 4. Чтение из систем | Автоматическая выгрузка из 1С/каталога, статусы и баланс при наличии методов | Подтверждённые API, схема данных, роли и тестовый контур |
| 5. Управляемая запись | Создание карточек и заказ КМ | Точные схемы API, журнал, согласование, защита от повторов |
| 6. Сопровождение | Регулярные проверки и обновления | Ответственный, восстановление, мониторинг ошибок и версии шаблонов |

## Условия прямой интеграции

**1С.** Платформа поддерживает HTTP/OData, но это не доказывает, что в базе компании опубликован подходящий интерфейс. Сначала проверить существующие обработки и согласовать чтение минимально нужных справочников и документов. Имена сущностей, URL и реквизиты не выдумываются. Прямое изменение SQL-базы вместо прикладного интерфейса не используется.

**ИС МПТ.** У оператора описаны СУЗ API, каталог маркируемых товаров и TRUE API. Для выбранной товарной группы нужны актуальные версии документов, тестовая среда, аутентификация и привязка роли. КМ эмитируются уполномоченной системой; локальный скрипт не может заменить официальную эмиссию.

**GTIN / NTIN.** Это разные идентификаторы. Нужно выяснить, кто у компании отвечает за создание/получение каждого, какие данные разрешено менять и где находится авторитетный источник. Проверка контрольной цифры GTIN не равна созданию GTIN. Каталог маркируемых товаров и общенациональный каталог нельзя автоматически считать одним API.

**Баланс.** Можно добавить чтение баланса и предупреждение при достижении согласованного порога, если доступен соответствующий метод. Размер порога рассчитывается по расходу КМ и сроку пополнения. Текущее приложение баланс не читает. Само пополнение остаётся действием уполномоченного сотрудника.

**Документы и ЭЦП.** Можно автоматизировать заполнение реквизитов и проверку комплектности. Подписание требует отдельно согласованного сценария, полномочий и совместимой инфраструктуры подписи. Закрытый ключ ЭЦП не размещается в GitHub и не встраивается в программу.

## Что добавить перед любыми производственными записями

- Сохранённый журнал операций и устойчивый ключ запроса, исключающий повторный заказ КМ при повторе запроса или таймауте.
- Предварительный просмотр и подтверждение конкретного пакета сотрудником.
- Очередь исключений и видимый статус каждой поставки.
- Сверку результата с системой после отправки: таймаут не означает, что операция не выполнилась.
- Ролевой доступ, служебные учётные записи, секреты вне кода, ограничение объёма данных в журнале.
- Тесты по актуальному контракту API и пилот в тестовом контуре. Текущие локальные тесты не являются тестами интеграции с компанией.

## Проверка пилота

Возьмите 3–5 разных поставок: обычную, с несколькими размерами/цветами, с дублями, с недостающими сведениями и с расхождением числа КМ. Сверьте все заблокированные строки и несколько прошедших, суммы количества по поставкам, соответствие артикулов, GTIN, NTIN и источников. Критерий внедрения — отсутствие неверно подготовленных строк на согласованной выборке и измеренная экономия с учётом исправлений и проверки.
